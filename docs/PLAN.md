# План развития: система управления сетью продуктовых магазинов

Основа — текущий код (касса на Flask + SQLite, Центр сети на Flask + PostgreSQL на Railway).
Фокус — **продуктовые магазины**: вес, сроки годности и партии, маркировка Asl Belgisi, 18+/алкоголь, поставщики.
Размеры/цвета (одежда, обувь) — не в приоритете; модель данных оставляет для них место (варианты товара, этап 3+).

Референс по функциональности — Lume Retail. Дизайн, название и фирменный стиль — **свои**.

---

## 1. Архитектура

```
 ┌──────────────── Магазин (оффлайн-first) ────────────────┐        ┌──────────── Облако (Railway) ────────────┐
 │  Касса (Flask + SQLite WAL, Chrome --app)               │  HTTPS │  Центр сети (Flask + PostgreSQL)          │
 │  • продажи, возвраты, смены, Z-отчёт                    │ ─────► │  • магазины, единый каталог, цены         │
 │  • фискальный модуль: FiscalDriveService :3449          │  /sync │  • остатки по сети, накладные/перемещения │
 │  • склад магазина: приход, ревизия, сроки, партии       │ ◄───── │  • сетевая аналитика и отчёты             │
 │  • клиенты, бонусы, насия, акции                        │        │  • переезд из 1С/BILLZ/МойСклад/Excel     │
 │  • аналитика магазина, Telegram-отчёты                  │        │  • раздача обновлений кассам              │
 └──────────────────────────────────────────────────────────┘        └───────────────────────────────────────────┘
```

Почему касса остаётся локальной: продажа и фискальный чек не должны зависеть от интернета.
Касса работает автономно и синхронизируется с Центром раз в минуту (идемпотентно по `uid`).

**Принципы учёта** (обязательны для всех модулей):
- Остаток меняется только через `stock_moves` (тип, количество, ссылка на документ, сотрудник, время) — триггеры следят за `stock`.
- Каждая операция сети — документ со статусом; повторная отправка не создаёт дублей (uid + `INSERT … ON CONFLICT DO NOTHING`).
- Важные действия — в `audit` (кто, когда, что, уровень важности); уровень 2 уходит в Telegram.
- Деньги — в сумах, округление до целых; время — Asia/Tashkent.

## 3. Структура базы данных

### Касса (SQLite, `data/kassa.db`)
- `settings`, `users` (роль), `audit`
- `categories`, `products` (uid, штрихкод, ИКПУ, цены розн./опт, мин. остаток, срок годности, маркировка, 18+), `product_barcodes` (упаковки)
- `stock_moves` (единственный источник изменения остатка), `batches` (партии со сроком)
- `shifts`, `sales` (оплаты нал/карта/QR/насия/бонусы, фискальный статус), `sale_items` (себестоимость, марки, акция)
- `purchases`/`purchase_items`, `suppliers`/`supplier_ops`, `docs`/`doc_lines` (накладные из Центра)
- `customers`/`customer_ops` (бонусы, долг, тип цен), `cash_ops` (внесения, изъятия, расходы)
- `promos`, `revaluations`/`revaluation_lines`, `parked`

### Центр (PostgreSQL)
- `stores` (токен кассы, последняя связь, версия), `products` (единый каталог), `stock` (магазин × товар)
- `sales`/`sale_items` (копия продаж всех касс), `docs`/`doc_lines` (поставки и перемещения)
- `imports`, `pending_stock`, `pending_customers`, `pending_history` (переезд)

### Добавится по этапам
- Этап 2 (готово): `users` (логин, роль, хэш пароля), `user_stores` (доступ к магазинам), `store_plans` (план по месяцам), `audit` (журнал Центра); в `stores` — управляющий, телефон, кассы, площадь, город, дата открытия
- Этап 3 (готово): `products.brand`; касса — `price_history` (пишет триггер БД при любой смене цены, с источником и сотрудником), `supplier_returns`/`supplier_return_lines`; Центр — `price_history`
- Этап 4 (готово): статусы в `docs` + `approved_at/approved_by/prepared_at/completed_at`, `transfer_events` (история каждого перехода); на кассе `docs.picking`
- Этап 5 (готово): `promocodes`, `promocode_uses`, `integration_log`; в `sales` — `promo_code`, `promo_disc`, `qr_provider`
- Этап 6 (готово): Центр — `money_ops` (кассовые операции, оплаты поставщикам и расходы Центра, идемпотентно по `uid`); в `sales` — `qr`, `qr_provider`, `promo_disc`; касса — `uid`/`synced` в `cash_ops` и `supplier_ops`
- Этап 7 (готово): Центр — `employees`, `employee_plans`, `customers`, `customer_stores` (бонусы/долг клиента в каждом магазине), `loyalty_levels`; в `sales` — `cashier_uid`, `customer_uid`; касса — `uid` у `users`/`customers`, `users.hq`, `customers.level/level_discount/level_cashback/synced`
- Этап 8 (готово): Центр — `integrations` (настройки, включено, последняя связь/ошибка), `integration_jobs` (очередь и журнал обмена: попытки, следующая попытка, ответ, ошибка)

## 4. Этапы

1. ✅ **UI/UX и Dashboard** — дизайн-система, навигация, Dashboard по ТЗ, ALERTS, уведомления, поиск по системе (касса и Центр).
2. ✅ **Роли и магазины** — пользователи Центра, 8 ролей, доступ по магазинам, карточка магазина, план продаж, сравнение филиалов.
3. ✅ **Товары и склад** — бренды, история цен, генерация штрихкодов, возврат поставщику, статусы остатков по сети.
4. ✅ **Перемещения** — согласование, отгрузка, приёмка, авто-рекомендации (скорость продаж 7/14/30/60 дней, излишки, нулевые остатки).
5. ✅ **Касса** — промокоды, Payme/Click через официальные API (после ключей), отчёт по кассиру.
6. ✅ **Аналитика и финансы** — фильтры по магазину/категории, сезонность, P&L и денежный поток по филиалам, PDF.
7. ✅ **Сотрудники и CRM** — карточки, план, рейтинг; уровни лояльности, сегменты, LTV.
8. ✅ **Интеграции и AI** — 1С, Didox, Tasnif, Uzum; AI-помощник по данным сети.
9. **Узбекский язык, тесты, запуск** — перевод интерфейса, нагрузочные тесты, бэкапы, документация API.

Каждый этап проверяется автотестами (продажа → остаток, возврат → остаток, перемещение → остатки двух магазинов, синхронизация без дублей) и скриншотами перед переходом к следующему.
